# Dropdown settings

Open **Admin → Learning & results → Dropdown settings** at `/admin/taxonomies`.

Choose a section, then use its Add button:

| Group | Choices |
| --- | --- |
| Education | Boards, Classes, Subjects, Languages, Programs |
| Locations | States, Districts |
| Institution & profile | Institution types, Qualifications, Designations, Experience |

Enter the name, display order and status. New classes require a board, new subjects require a class, and new districts require a state. Create those parents first and keep them active. All pages of available parents are loaded; loading failures block new dependent choices.

Search and status filters apply to the selected section. Switching sections clears those filters and returns to page one. Reopen a book or other form after adding options to load its latest dropdown choices.

Existing relationships stay fixed during editing. Names, status and display order remain editable, subject to the existing backend safeguards for referenced records. Archive keeps historical references; the backend can refuse archival when active dependents still exist.

Internal types and keys are hidden from the normal interface. Keys are generated by the existing backend creation service, including parent keys and duplicate suffixes. Existing IDs and keys are preserved. The supported types remain fixed because each type has specific application uses.

This interface change retains the existing route, APIs, collections, optimistic revisions, CSRF protection and `content.read`/`content.write` permissions. It does not migrate application data or change public book/category behavior. The Programs dropdown is a shared reference list; actual college admission programs remain managed under their college.

Verification commands:

```powershell
cd frontend
node --test --test-concurrency=1 tests/dropdown-settings.browser.test.js tests/admin-concise-help.browser.test.js
npm.cmd run build
```

The browser tests use mocked HTTP responses and do not write to the application database. They cover grouping, type-specific creation, parent requirements, edits, archival payloads, missing/failed parent loading, permissions, keyboard access, mobile layout and accessibility. Real database regression tests require a separately configured isolated database; mocked browser checks do not establish database acceptance.

Verified on 2026-10-28: all six grouped-settings scenarios and all four existing concise-admin scenarios passed. The frontend production build passed with the existing large-chunk warning. A first browser run exposed an ambiguous parent-select accessible name; explicit accessible names were added and all grouped-settings scenarios passed on rerun. No real database tests or the full historical browser suite were executed for this interface change.
