## Calendar and compatibility rules

Calendar arithmetic uses UTC, preserves time of day and clamps the original day to the last day of the destination month: 29 February 2024 + 12 months becomes 28 February 2025; 31 January + one month becomes 28/29 February. Explicit days remain elapsed 24-hour days. No schema default mutates historical plans. The default applies only when creating a positive-priced plan through the existing validated service. Free plans require an explicit supported duration. Existing expired-free and revoked-enrollment review gates are preserved; automatic free-period renewal is not added. To change a historical day plan to a month-based plan, create a replacement plan; do not change both units on an existing plan. Editing current plan duration never rewrites captured order snapshots or enrollments.

Existing policy values remain compatible: omitted document `required` means required; omitted registration `enabled` retains the existing active-policy behavior; omitted guardian applicability means minors. Admin review, active verified-account eligibility and captured paid-fee activation are mandatory safety conditions, not configurable bypasses. Document suggestions are advisory only and do not introduce unsupported institution registration categories.

## HTTP/configuration changes

- Existing `GET/PATCH /api/v1/admin/business-policies`: optional registration fields, `refunds`, `franchise` and expanded `invoice` metadata; main-admin save, reason and expected revision remain required. Responses expose bounded change history.
- `GET /api/v1/public/registration-config`: per-category unavailable reasons; required-document list excludes optional slots.
- `GET /api/v1/public/franchise-fees`: effective fee configuration and gated renewal status; no applicant input, mutation, payment or private application data.
- `GET /api/v1/me/refund-policy`: signed-in request eligibility options. Existing refund request accepts `reasonCategory`; backend chooses eligibility from the order's actual category, never the frontend.
- Existing result record action namespace gains `/submit`, `/approve`, `/reject`; listing accepts `reviewStatus`. Existing publish/correction/withdraw paths remain.
- Existing course plan API accepts `durationMonths` alongside legacy `durationDays`, with exactly one unit for active plans. Existing order/Checkout/verification/webhook contracts remain.

No environment variable or real `.env` was changed. No provider gate was enabled.
